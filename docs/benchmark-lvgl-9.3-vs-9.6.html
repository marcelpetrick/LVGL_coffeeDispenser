Did LVGL 9.6 get faster?

On this workload: yes, by about 7% of render time per fully redrawn 800×480 frame — measured as eight back-to-back pairs, because on this machine the absolute numbers drift further than the effect. The memory bill moved the other way: +16% peak RSS, while LVGL's own heap grew only 3%.

Eight pairs, not two averages

Each pair ran back to back on the same pinned core, 9.3.0 first: same clock state, same background load, so the difference inside a pair is the library and not the machine. The absolute level wanders by more than 10% across the session — that is the reason for pairing, and the reason a single before/after run is worthless here.

Where the frame time goes

Rasterization plus the handover of the finished buffer to SDL. Only the first half is LVGL's own work, and only the first half moved.

The memory bill

Measured in-process: lv_mem_monitor() for the pool LVGL manages itself — the number an embedded integrator sizes — and ru_maxrss for the whole process, which also carries the SDL window, the frame buffers and the C library.

The split is the interesting part: LVGL's managed pool barely grew, so the extra 1.8 MB is not allocations LVGL tracks. It sits in what the library allocates outside that pool and in the binary itself — more code, more static data, larger draw and cache structures. On a target where the LVGL pool is the constrained resource, 9.6 costs 1.3 KB more; where total RAM is the constraint, it costs about 1.8 MB.

Is 7% a good improvement?

For what it costs the integrator, yes. It arrives by bumping a submodule: no configuration change, no visual difference, and on our side only a handful of deprecated calls to migrate. Those ~350 µs per frame are CPU time handed back to the application, and they compound with every redraw.

It is well under the “up to 1.33×” the release notes advertise — expected, not suspicious. That figure is a best case on the boards LVGL measured: ARM cores, usually RGB565, with the blend paths that got the most attention. This run is x86-64, XRGB8888, one draw unit, and a UI of large opaque fills, rounded panels and text. The honest reading: a real single-digit gain on hardware LVGL did not optimise for, paid for with about 1.8 MB more resident memory. If RAM is the binding constraint on your target, that trade needs checking before the upgrade, and the LVGL pool figure above says the growth is not in the part you size yourself.

Did we measure the right thing?

Partly, and one earlier version of this page did not. It reported 1.23× from a single before/after round; repeating it as pairs put the same comparison at 7%. The first number was machine drift, and it is corrected here rather than quietly dropped.

  • Measured CPU time inside the render pass. The probe brackets LV_EVENT_RENDER_START to LV_EVENT_RENDER_READY, so the main-loop delay, the tick handler and the application logic stay outside the number. That is the quantity an embedded integrator budgets.
  • Method Pairs, because this machine drifts. A hybrid CPU on a powersave governor, sitting at 96 °C with an indexer running, moved the absolute render time by more than 10% between rounds — several times the effect. Only alternating runs survive that; sequential averages do not.
  • Workload A full-screen invalidation every refresh. Comparable and worst-case, but not typical: a real HMI redraws a progress bar, not 384 000 pixels. A partial-redraw benchmark weights small blends and clipping far more heavily.
  • Format XRGB8888 at 32 bpp only. Most LVGL targets run RGB565, and the renderer has separate paths per format, so this says nothing about the one most devices use.
  • Machine x86-64 laptop, single draw unit. None of LVGL's ARM SIMD paths are exercised. Four software draw units were tried and returned 4%, so the threads were not worth their cost here.
  • Not measured Presentation and input latency. The SDL dummy driver means no GPU, no compositor, no vsync, so the frame budget is a CPU budget and not a time-to-photon.
  • Not measured Which allocation grew. The memory numbers are peaks, not a profile: they say how much and where it is not, not which structure got bigger.
