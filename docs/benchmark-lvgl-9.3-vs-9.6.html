Render benchmark · LVGL Coffee Dispenser HMI

Did LVGL 9.6 get faster?

For the software renderer on this workload: yes, by about 6% — 4916 µs down to 4616 µs of CPU time per fully redrawn 800×480 frame. Ten pinned runs per version, distributions that do not overlap, and a memory bill that went up while the clock went down.

Flush per frame +1.0% 3525 → 3562 µs · noise

Every run, both versions

Each dot is one 5-second run: the mean time LVGL spent rasterizing a fully invalidated frame. The two clouds do not touch — the slowest 9.6 run is still faster than the fastest 9.3 run — which is what makes a 6% difference believable on a machine this noisy.

Where the frame time goes

A frame costs rasterization plus the handover of the finished buffer to SDL. Only the first half is LVGL's own work, and only the first half moved.

All values in microseconds. A second, interleaved A/B measurement — 10 alternating rounds of the two binaries on the same pinned core — put the gap at −8.0% on the median, so the effect survives a different run order.

Is 6% a good improvement?

For what it costs the integrator, yes. It arrives by bumping a submodule: no configuration change, no API migration for our code, no visual difference. On an embedded target the same 300 µs per frame is CPU time handed back to the application, and it compounds with every redraw.

It is also well under the “up to 1.33×” that the release notes advertise — and that is expected, not suspicious. That figure is a best case on the boards LVGL measured: ARM cores, usually RGB565 buffers, with the blend paths that got the most attention. This run is x86-64, XRGB8888, one draw unit, and a UI made mostly of large opaque fills, rounded panels and text. Different pixel format, different code paths, different ceiling. The honest reading: the optimization is real and free, our workload collects roughly a fifth of the headline number, and the price is a bigger binary and about 1.8 MB more resident memory.

Did we measure the right thing?

Partly. The measurement is sound for what it covers, and what it covers is narrower than “LVGL got faster”.

  • Measured CPU time inside the render pass. The probe brackets LV_EVENT_RENDER_START to LV_EVENT_RENDER_READY, so the main-loop delay, the tick handler and the application logic are all outside the number. That is the quantity an embedded integrator budgets.
  • Workload A full-screen invalidation every iteration. Comparable and worst-case, but not typical: a real HMI redraws a progress bar, not 384 000 pixels. A partial-redraw benchmark would weight small blends and clipping far more heavily and could land somewhere else entirely.
  • Format XRGB8888 at 32 bpp only. Most LVGL targets run RGB565. The renderer has separate paths per format, so this result says nothing about the one most devices use.
  • Machine x86-64 laptop, single draw unit. None of LVGL's ARM SIMD paths are exercised, and a hybrid CPU with a powersave governor needed core pinning before the numbers held still — the unpinned runs scattered by ±1300 µs and pointed the wrong way.
  • Not measured Presentation and input latency. The SDL dummy driver means no GPU, no compositor, no vsync. Flush here is a memcpy-grade upload, so the frame budget is a CPU budget, not a time-to-photon.
  • Not measured Where the extra 1.8 MB went. Peak RSS and binary size are single observations from this configuration, not an allocation profile. If memory is the binding constraint on your target, that is the number to chase next — and it moved more than the render time did.

Method

Harnessscripts/run_render_benchmark.sh --runs 10 --duration-ms 5000 --pin-cpu 0
AppLVGL Coffee Dispenser 0.9.0, release build
Display800×480, XRGB8888, SDL dummy driver
RefreshLV_DEF_REFR_PERIOD 33 ms, so ~30 fps is the ceiling
CPUIntel Core i9-12900H, pinned to CPU 0
CompilerGCC 16.2.1, -O3, identical flags for both
Configidentical, except LV_COLOR_DEPTH 32 vs LV_COLOR_FORMAT_DEFAULT XRGB8888
Memorypeak RSS via /usr/bin/time, 2 runs per version
Raw per-version reports live in the repository as LVGL_9.3.0_benchmark.md and LVGL_9.6.0_benchmark.md. Reproduce either with the harness command above.
